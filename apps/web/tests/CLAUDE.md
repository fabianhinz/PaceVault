# Testing Strategy

- **Goal**: Protect behaviour the user would notice breaking — wrong numbers, lost/duplicated/leaked data, a broken flow. Not coverage. A change usually needs 0–3 new tests.
- **Always test**:
  - persist `migrate` functions, including legacy and unrecognised shapes (data must survive)
  - Zod `safeParse` fallbacks for file, API and IndexedDB input (fallback, never throw)
  - dedup/merge when importing activities
  - secrets never reaching URLs, logs or storage
  - a regression test for every bug fix, named after the bug
- **Test when**: the logic branches, does arithmetic, or transforms data. Cover the happy path plus edge cases you can point to in a real FIT file, API response or bug report — not hypothetical inputs.
- **Skip**: trivial helpers, thin wrappers, pass-through mappings, components without behaviour of their own, and exact request shapes unless they carry a security property.
- **Rendering**: Component and hook specs mount through `renderWithProviders` / `renderHookWithProviders` (`@testUtils/render.ts`), never testing-library's bare `render`/`renderHook`, and bind the result whole (`const view = renderWithProviders(…)`, `const hook = renderHookWithProviders(…)`); pass `createTestQueryClient()` (`@testUtils/queryClient.ts`) only to seed or inspect the cache; stub viewport and pointer queries with `window.matchMedia = createMatchMedia(width)` (`@testUtils/matchMedia.ts`).
- **Queries**: Component specs find elements the way a user does — `getByRole` (with an accessible `name`, never a positional index), `getByText`, `getByLabelText` and their `queryBy`/`getAllBy` forms — called on the render-helper result bound whole (`const view = renderWithProviders(…)`, `view.getByRole(…)`), never destructured and never through `screen`. `*ByTestId` only for elements with no accessible identity (spinner, presentational wrapper, `iframe`) or for a stub the spec renders from `vi.mock`; no `container.querySelector`. Wait with `await waitFor(() => expect(…))`, not `findBy*`; scope with `within(node)`. Never add a `data-testid` to app markup where a label or `aria-label` would do.
- **Level**: A unit spec builds its subject directly and replaces every collaborator one layer below it with a `mock<T>()` / `mockDeep<T>()` substitute from `vitest-mock-extended`; it never lets the production wiring assemble the real graph. `packages/engine`, `packages/gpx` and `src/lib/` get unit specs. An `*.integration.spec.ts` exists only where the wiring itself is the behaviour (e.g. import → engine → store) — one spec per flow, plus one for a failure the user sees — and substitutes only what leaves the process (`fetch`, `Worker`, an IndexedDB failure). Never repeat a case at a second level.
- **E2E**: Only core user journeys. Extend an existing spec before adding a new file.
- **Style**: Assert outcomes (values, persisted state, visible text) and, on substitutes, the interactions with their arguments; not internal structure or snapshots (one exception: file-format output, see `packages/gpx/CLAUDE.md` § Rules, Tests). Substitutes are `let` at describe scope and rebuilt in `beforeEach` (`clearMocks` clears calls, not stubbed return values); reach a module-mocked export through `vi.mocked(x)`, never a cast; title the top-level `describe` with the subject's symbol (`describe(subject.name, …)`) except for zustand store hooks and zod schemas.
- **Assertions**: Interactions with their arguments (`toHaveBeenCalledWith`; bare `toHaveBeenCalled` only for a call whose arguments the spec does not determine), absence as `.not.toHaveBeenCalled()`; `toBe` for primitives, `toEqual` for objects and arrays; booleans as `toBe(true)`/`toBe(false)`, never `toBeTruthy`/`toBeFalsy`; never a computed predicate — `toContain`, `toContainEqual`, `toHaveLength`, `toThrow`/`rejects` or `filter(…)` against `[]`; DOM facts through jest-dom (`toBeInTheDocument`, `toBeDisabled`, `toHaveValue`); no file snapshots, inline snapshots only for short literal text (exception: file-format output, `packages/gpx/CLAUDE.md` § Rules, Tests). A new matcher is registered with `expect.extend` in `apps/web/tests/setup.ts` and declared in `apps/web/tests/types/`, never written as a helper that wraps `expect`.
- **Existing tests**: Don't add tests to files you didn't otherwise touch. If a test fails because behaviour changed on purpose, update or delete it — don't add a sibling.
- **Naming**: App specs live in `apps/web/tests/`, package specs in `packages/<p>/tests/`, workbench specs in `tools/workbench/tests/`, named `<subject>.spec.ts` (`.spec.tsx` when the spec contains JSX). Several specs for one subject keep the mirrored path and add a qualifier before `.spec` (`chartData.integration.spec.ts`, `fit.laps.spec.ts`); there is no `.test.ts` suffix.
- **Location**: Specs mirror the source folder structure: `src/<path>/<file>.ts` is specified in `tests/<path>/<file>.spec.ts` of the same package, e.g. `apps/web/src/lib/chartData.ts` → `apps/web/tests/lib/chartData.spec.ts`, `packages/engine/src/zones.ts` → `packages/engine/tests/zones.spec.ts`. An app spec that exercises engine code through an `@/` module sits at that module's mirrored path. Never place a spec under `src/`; move or rename a spec in the same change as its subject. A spec's own fixtures sit beside it; helpers shared by several specs live in `apps/web/tests/testUtils/`, imported as `@testUtils/<module>.ts`; ambient test declarations go to `apps/web/tests/types/*.d.ts`.
- **Factories**: Every entity a spec needs comes from a `createMock<Entity>(overrides?)` factory that returns a complete instance; pass only the fields the test turns on. Engine entities (sessions, records, laps, GPS, PBs, daily metrics) from `@pacevault/testing/<entity>.ts`, record/lap/session series from `@pacevault/testing/series.ts` (engine tests import both by relative path, `../../testing/src/…`, to avoid a workspace cycle); app entities (profile, coaching, workout step, weekly plan) from `@tests/factories/<module>.ts`. No local `make…` helpers and no entity object literals in specs; factory modules are imported by specs only.
- **Setup**: `tests/setup.ts` (fixed date, store reset, fake IndexedDB) runs for app tests only; a package test that needs a fixed date sets it itself.
- **Imports**: Test APIs (`describe`, `it`, `expect`, `vi`, …) are imported from `vite-plus/test`, not `vitest`.
