# Map hover flashes: code paths

Owner report: hovering list items (sessions, segments) drives the map background; clicking through to a detail page sometimes shows a short "flash" of other layers ("all tracks > single > all tracks flash > detail page"). This file lays out the code paths, it does not fix anything. All `path:line` references are against the working tree of `feat/segments` on 2026-11-04; paths are relative to `apps/web/src/` unless they start with `node_modules/` or `tools/`.

## TL;DR

Two clocks drive what the map draws, and they tick at different times:

1. **Hover state** lives in three Zustand stores and is written synchronously from pointer handlers. A Zustand write is a blocking (sync-lane) React update.
2. **Route state** comes from react-router 7's `BrowserRouter`, which wraps every location update in `React.startTransition` (`node_modules/.pnpm/react-router@7.13.0_react-dom@19.2.4_react@19.2.4__react@19.2.4/node_modules/react-router/dist/development/chunk-JZWAC4HX.mjs:9845-9851`; the app uses the plain `<BrowserRouter>`, `routing/AppRouter.tsx:5`). The new route commits **after** any sync update made in the same click.
3. A third clock sits behind the route: `openedSessionId` and `focusedTripSessionIds` are **copied from the route into a store by `useEffect`** (`components/mapBackground/hooks/useOpenedSessionEffect.ts:5-7`, `components/trips/hooks/useTripMapFocusEffect.ts:5-10`). They lag the route commit by one more commit.

Each map layer hook derives "what to show" on its own from some mix of these three. Whenever a click clears hover (clock 1) before the route (clock 2) or the effect mirror (clock 3) has caught up, the hooks see the "overview, nothing hovered" state for one or more frames and draw every track. `gps-tracks` animates colour over 300 ms (`components/mapBackground/trackColors.ts:63`, applied at `components/mapBackground/hooks/useTrackLayers.ts:62-63`), so the stale frame shows as tracks starting to fade back in, then vanishing when the route lands.

## 2. Click-through sequences, frame by frame

React timing facts the sequences rely on:

- A Zustand `set` from a click handler is a sync-lane update: React renders and commits it at the end of the event, before the next paint.
- `pageRouting.open` (`routing/usePageRouting.ts:13-15`) calls `navigate`; `BrowserRouter` applies the new location inside `startTransition` (chunk `:9845-9851`, see TL;DR). The transition renders after the sync work and may yield across frames while the new page renders.
- Passive effects (`useEffect` and its cleanups) of a sync commit run right after that commit. Those of a transition commit are scheduled, so the browser usually paints the transition commit once **before** they run.
- deck.gl `transitions` interpolate an attribute from its current GPU value to the new one; a layer that is dropped from the list (hook returns `null`) disappears at once, with no fade.

### S1. Segments tab card → segment page (the reported flash)

Start: Dashboard `?tab=segments`, pointer on a card. W6 set `hoveredSegmentId`; R1 painted every `gps-tracks` path at alpha 0 (`useTrackLayers.ts:40-41,73-74`, faded out over 300 ms), R2 draws the hovered segment (`useSegmentLayers.ts:106-111`). The user sees one line.

1. **Click, sync commit.** `SegmentItem.tsx:15` → `SegmentsTab.tsx:33` → `hoveredSegmentId = null`. Then `SegmentItem.tsx:16` → `navigate` (queued as a transition). Render with the route still on the tab: `segmentHovered` false, so the `getColor` trigger changes (`useTrackLayers.ts:90`) and every track goes back to `ALPHA_BY_TRACK_INTENSITY` with a 300 ms transition (`:62-63`); `segment-hover` turns invisible (`useSegmentLayers.ts:56`). **Frame A: the selected segment vanishes and all tracks start fading in.**
2. **Transition render and commit**, some frames later (the segment page renders the header, pass list, scatter and charts explorer). `useSegmentMapTracks` sees `pageMatch` (`useSegmentMapTracks.ts:56,66-67`) → mode `page`. R1 returns `null` (`useTrackLayers.ts:58-60`): the half-faded tracks disappear at once. R2 draws `segment-track` from the segments store (`useSegmentLayers.ts:112-114`; geometry is in the store, `useSegmentDetail.ts:18-20`, so it is there at once). R3 switches to `{ kind: 'segment' }` (`useMapCameraTarget.ts:26`) and the camera flies. **Frame B: one line again.**

What the eye sees: one line → all tracks flicker in → one line. Duration = time between the sync commit and the route transition commit, longer the heavier the target page.

## 3. Root cause

**The map has no single source for "what to show". Each layer hook derives its mode from a mix of route state (committed in a React transition), effect-mirrored route state (one commit later) and hover state (sync Zustand writes, cleared on click, pointer leave or unmount depending on the call site). Whenever these three disagree for a frame, the hooks fall back to their default, which is "overview, all tracks, nothing hovered", and the 300 ms alpha transition makes that default visible.**

Where the pattern is duplicated:

1. **Three hover stores, five hover fields, four clearing policies.** `mapFocus.hoveredSessionId` / `hoveredStudioRouteId` (generic `useMapHover`, clears on leave + unmount), `segmentFocus.hoveredSegmentId` (hand-rolled `onHoverChange`, clears on leave + **click**, never on unmount), `mapControls.hoveredSegmentSpan` (hand-rolled, clears on leave + click, reset only by session open/close), `hoveredLapIndex` (leave + effect cleanups in two places). The segment rows do not use `useMapHover` at all; `useMapHover.ts:5-8` only knows `session` and `studioRoute`.
2. **Clear-on-click** (`SegmentItem.tsx:15`, `SessionSegmentItem.tsx:28`) and **clear-via-popup-close** (`SessionsPickPopup.tsx:27`, `StudioRoutesPickPopup.tsx:26`) both clear hover synchronously, before the transitioned route commits. These are the S1, S2, S6 flashes.
3. **Route mirrored into a store by effect**: `openedSessionId` (F1) and `focusedTripSessionIds` (F2), while segment and studio focus are read from the route directly (F3, F4). So two clocks exist even without hover: S4, S5, S7.
4. **Mode derived in several hooks**: R1 (`useTrackLayers.ts:58`), R1' (`useMapTracks.ts:25`), R3 (`useMapCameraTarget.ts:22-36`), R2 (`useSegmentLayers.ts:105-114`) each decide what is shown with their own condition list; R1' ignores segment pages, R1 ignores trips, R3 gives segment priority over session while R1 gives session priority. `useSegmentMapTracks` and `useStudioMapTracks` are recomputed in 4 and 6 hooks.
5. **Fades on hover-driven alpha**: `HIGHLIGHT_TRANSITIONS` on `gps-tracks` and `studio-routes` animate any stale frame for 300 ms instead of showing it for one frame.

Adjacent findings (not flashes, but the same seam): `hoveredSegmentId` survives a `VirtualItemList` row unmount or tab switch without a pointer leave and comes back when the Segments tab is shown again; `hoveredPassSessionId`, `passMarker`, `bestMarker` are never cleared on leaving a segment page, so stale markers can show on the next segment page.

## 4. Fix options (sketches, no code)

### O1. One map-focus model, derived during render from route + hover (recommended)

- One hook (or one pure function plus a thin hook), e.g. `useMapScene()`, returns a discriminated union: `overview{ hover }`, `trip{ ids, hover }`, `session{ id }`, `segmentTab{ hoveredSegmentId }`, `segmentPage{ id }`, `studioTab{ hover }`, `studioRoute{ id }`. It reads the **route directly** (as F3/F4 already do) and the hover fields; `openedSessionId` and `focusedTripSessionIds` stop being effect mirrors (session open/close resets move to the route change or to the scene switch).
- Every reader (R1, R1', R2, R3, R4, R6, `useMapPopupState`) switches on the scene instead of its own condition list, so all layers change in the same commit.
- Hover is applied only when its scene matches (`hoveredSegmentId` only in `segmentTab`, `hoveredSessionId` only in `overview`/`trip`, …), so a stale hover can never resurrect "all tracks"; clearing hover on click becomes unnecessary and is removed (`SegmentItem.tsx:15`, `SessionSegmentItem.tsx:28`). Pick popups close after navigation, or their hover clear is ignored because the scene already changed.
- One generic hover hook for every list (sessions, studio routes, segments, segment rows) with one clearing policy (leave + unmount), ideally one hover field `{ kind, id }` in one store.
- Files: `store/mapFocus.ts`, `store/segmentFocus.ts`, `store/mapControls.ts` (hover fields), `components/mapBackground/hooks/useMapTracks.ts`, `useTrackLayers.ts`, `useSegmentLayers.ts`, `useSegmentMapTracks.ts`, `useStudioMapTracks.ts`, `useStudioRouteLayer.ts`, `useDetailLayers.ts`, `useSessionDetailPath.ts`, `useMapCameraTarget.ts`, `useMapCameraInputs.ts`, `useMapPopupState.ts`, `useOpenedSessionEffect.ts`, `useMapBackgroundEffects.ts`, `useMapHover.ts`, `components/trips/hooks/useTripMapFocusEffect.ts`, the list items (W1–W7), plus specs and the e2e map tests.
- Risk: medium-high. Wide touch on the map, camera and lap code; `setOpenedSession` side effects (control resets, `mapPadding.ts:18` reads `openedSessionId` imperatively) need a new home. Fixes S1–S7 at the cause.
- Note: with the route read from `useLocation`, the hover writes are still sync and the route still a transition, but because every hover read is gated by the scene, the in-between frame is "same scene, no hover", which in S1/S2 is still the overview. To close S1/S2 fully O1 needs one of: (a) do not clear hover on click/close (leave it to unmount after the route commits, like S3), or (b) apply the hover clear inside the same transition as the navigation. (a) is the simpler rule and falls out of the generic hover hook.

### O2. Keep the previous layer set until the next scene is ready

- A small "scene latch" in `DeckGLOverlay`: when the route changes, keep rendering the last committed layer list until the new scene has its data (segment in store, session records loaded, trip ids set), then swap. Hover clears during the latch are ignored.
