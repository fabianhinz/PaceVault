# Segments: stretches you save and compare

## Context

Segments are stretches the user saves: a range selected on a session's charts ("Save as segment", desktop) or a whole session from its ⋯ menu ("Use as reference segment") (Q95). On save the app finds the sessions of the same sport that ride the reference and computes their passes; later imports are matched against every saved segment (Q95, Q96). Segments live in a Dashboard tab, in a Segments row of the session summary card and on their own page `/segments/:id` with pass times, a selected-vs-best charts explorer and a map. The automatic detection built first is removed: on real data it produced 1432 overlapping segments. Look and behaviour: `mockup/hifi/` (segment page), `research/user-segments/` (wireframes W1–W7 of the creation flow); `tech.md` holds modules and interfaces.

## Decisions (settled)

Creation

- The user creates every segment; there is no automatic detection, no types (Climb, Flat, Descent, Route), no numbering (Q95, replaces Q10, Q24, Q31, Q35, Q57, Q58, Q91, Q93).
- From the charts (desktop only, Q99): a drag-zoom range shows a "Save as segment" pill with the `SplinePointer` icon next to Reset zoom (Q98); it opens the name dialog prefilled with "<session name> · km a–b" (Q101); Save opens the segment page at once (Q96).
- From the session ⋯ menu: "Use as reference segment" turns the whole session into a segment (name dialog prefilled with the session name); when the session already is a reference the entry reads "Open segment" (Q102).
- Both entries are offered for sessions with GPS, for a range of any length; there is no minimum length (Q107). A range with fewer than two GPS points gives no segment and a snackbar.
- The name dialog shows a hint when the new stretch overlaps a segment of the same sport: at least 50 % of the new stretch's length runs along that segment in the same direction; the most overlapping one is shown as a small segment item (sport-tinted `SplinePointer` tile, name, its distance) that opens it; Save stays possible (Q108, changed in R91 from "nearly the same start and end"). Owner: "lets go with b, users are still able to choose from the dialog"
- After Save the segment page shows its header at once and skeletons while matching, then the passes (Q96, W7; the "Finding passes…" line went with R53, the one-pass note with R79).

Matching

- Same sport (Q8), same direction (Q3), one pass per session, its best (Q8); every pass counts (Q59). A session counts when it rides the reference within a 30 m corridor, covers at least 95 % of it and passes within the end tolerance of both ends; the end tolerance is 1 % of the segment's length, at least 50 m and at most 200 m (a 2 km stretch 50 m, a 12 km route 120 m, from 20 km 200 m); corridor and coverage do not change with the length (Q105).
- The reference is read, not stored: matching reads the source session's records, cuts them at the stored start and end and resamples them to 10 m (Q106).
- Matching runs in a Web Worker (bbox prefilter on the stored session bounds, then the corridor match on the candidates' records) and is cached per segment in IndexedDB; the cache records which sessions were checked, so an import, a reprocess or a delete re-matches only what changed, and the passes of a deleted session drop out.
- Matching runs lazily when the Segments tab, a session detail or a segment page needs passes, like the personal bests (Q81, Q82); the previous passes stay visible while it runs, without a note.

Persistence

- Segments are user data in a persisted Zustand store `store-segments`: id, name, sport, the source (session id, kind, start and end cut), distance, net elevation, a display polyline and bounds encoded like `session-gps`, created (Q106). No reference geometry is stored; the passes cache lives in the IndexedDB store `segment-passes`.
- The cuts are record timestamps (elapsed seconds of the first and last record of the stretch): every record has one and a reparse keeps them, while `distance` is optional per record; `recordSpanBetween` (`apps/web/src/lib/analysis/laps.ts:128-143`) turns them back into the record slice.
- A segment belongs to its source session: deleting the session deletes its segments (store entries and passes cache), and the session's delete dialog warns "This also removes n segments created from it: …" with their names (Q106).
- `DB_VERSION` 5 is redefined (it never shipped, Q109); the owner clears the local site data once in the browsers that ran the round-1 build. Delete all data clears segments.

## Risks

- `DB_VERSION` 5 is redefined: a browser that ran the round-1 build already sits at version 5 with the old `segments` store and never gets `segment-passes` until its site data is cleared (Q109, owner step in Delivery).
- Long whole-session references read many records on the first save; the bbox prefilter only helps where routes differ.
- The reference is derived from the source session's records on every full match: a reprocess that re-parses the FIT replaces those records (`bulkReplaceSessionData`, `apps/web/src/lib/analysis/reprocessSessions.ts:162-169`), so the reference and all passes can shift slightly; the cache's `sourceSessionKey` forces a full re-match then, while the stored display polyline, bounds, distance and elevation keep their creation values. The cuts are record timestamps, which a re-parse keeps.
- Deleting a session now deletes the segments made from it with all their passes, also when other sessions ride them; the dialog names them before the delete (Q106).
- The similar-segment hint compares only the ends and the length: a segment with the same ends but another way between them (a detour) is hinted as similar; Save stays possible, so the cost is one extra line.
- Loops (start = end) and out-and-back routes: the start matches several visits and the reverse leg must stay out; covered by `startPerVisit` and the bearing check, to watch on real data.
- Same-polyline demo data does not exercise the tolerances; e2e relies on it, the engine specs carry the tolerance cases.
- Removing detection deletes uncommitted code; the snapshot in `research/detect-bench/` keeps it for `segment-suggestions`.
