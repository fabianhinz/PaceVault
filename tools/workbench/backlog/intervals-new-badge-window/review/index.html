Intervals sync: faster downloads and a 30-day window for the "new" badge

intervals.icu imports download 5 files at a time, never faster than 5 requests/s. The sync window grows to 30 days and now also decides which sessions get the blue badge. Round 1: "Delete all data" now stops a running intervals sync.

Review round 1

R1–R3 were already there before this item. "Delete all data" reset the stores but let a running background sync go on: it kept downloading, wrote its sessions back into the emptied app, and the next connect waited for it. Confirmed by an e2e probe. No UI change, no screenshots.

R1Import showed no progress

Fixed. Delete all data cancels and removes the intervals-sync query, and its abort signal reaches every intervals.icu request (including one still waiting for its pacer slot). The next connect no longer waits for an old run, so the dialog counts up from the first file.

Fixed by the same change: the aborted run records no activity ids, so the new connect imports everything and the summary counts it (e2e: "3 new sessions").

R3Deleted intervals sessions came back

Found by the probe. Fixed: after the abort, no further download is started, nothing is parsed into the batcher, and a save already running writes no further IndexedDB chunk and adds no session. A chunk written before the abort commits before the delete's own clear, so it is wiped. File uploads pass no signal and behave as before.

Speed measured

100 synthetic FIT files (1 h, 1 Hz), new user, dev server. FIT upload: 1.9 s from click to summary (parse 13 ms per file, two saves of about 265 ms). intervals.icu with a mocked 100 ms download: 21 s, of which 18.6 s is waiting for downloads, so the 5/s pacer sets the floor (20 s per 100 activities); parsing and saving don't limit it.

Measured with a throwaway Playwright harness, removed after the run.

Changes without UI

No UI change, no screenshots.

C1Every intervals.icu request is paced at 5/s

Each request waits for its slot, slots at least 200 ms apart (Q1). This covers the listing, the key check, /file and the /fit-file fallback.

apps/web/src/lib/api/intervals.ts:35, :63. Test: apps/web/tests/lib/api/intervals.spec.ts.

C2Up to 5 downloads in flight, saved newest first

Downloads run up to 5 ahead; parsing and saving stay one at a time in listing order. A 429 or 401 still stops the import; downloads already in flight are dropped (their requests still go out, at most 4) and the next background sync fetches them again.

apps/web/src/lib/api/intervalsImport.ts:21, :93, :163. Test: apps/web/tests/lib/api/intervalsImport.integration.spec.ts.

C330-day window, also for the "new" badge

The window is newest intervals session minus 30 days. Only sessions starting inside it get the badge, in foreground and background runs alike; with no intervals session yet (first connect) nothing is badged. Backlog activities from years ago stay unbadged.

How to check

  1. Connect a large intervals.icu account: the import progress moves clearly faster than before, and DevTools → Network shows at most 5 requests per second and no 429.
  2. With more than 2,000 activities, wait for the background sync that continues the backlog: the older sessions arrive without the blue badge.
  3. Record or upload a new activity to intervals.icu: after the next sync (focus the window or wait up to 15 min) it shows the blue badge.
  4. R1–R3: with a key saved, reload Settings so the background sync starts, press Delete all data while it downloads, then onboard again with the key. Network shows no further /file requests after the delete, the dialog counts up, the summary names the imported sessions, and no session from before the delete comes back.
  5. Tick the two real-data checks in plan.md when they hold.
